# v18 callback isolation and completion lifecycle repair

AdapterObserve now resolves native ID before considering a target path, and only unbound pending requests may bind by path. Cancelled/terminal task results are immutable. This fixes a reproducible previous search-order bug where an earlier native callback could bind to a newer retry at the same target. Registry records retain their original IDs, including after event release, to route late callbacks safely.

The original EXE success entry at VA 4b7c80 posts DownloadSuccessHandler (4b8750) to task thread 3; the hook observes success before that queued handler retires the active row. adapter_task_pending distinguishes this callback from actual manager-vector retirement. The worker waits with short sleeps (up to 5 seconds) before verification/publication; failure/cancel retires the old task and waits before submitting a replacement at the same path. A retirement timeout is surfaced instead of overlapping transfers.

file_retry.h retries only Win32 sharing/lock/access errors 32/33/5, bounded to 60 sleeps of 50ms per operation. The production verifier now preserves its API error and sets ERROR_CRC for size/SHA mismatch, so stale last-error cannot misclassify corruption as a lock. Cache move/copy and verification reuse the policy; stop/cancel interrupts it. No read-sharing with active writers, hash bypass or new HTTP provider is introduced. Persistent access problems still fail after the bound.

Before the web terminal state is published, group state is finalized and adapter_group_sync uses the pointer-free original UI dispatcher to synchronously invoke both original observer methods, with a 2-second timeout. Delayed delivery remains safe and does not poison UI request storage. Timeout is logged and shown as an install warning. Failed groups (state 3) no longer project into active lists/counts, and are not fabricated as successful history. Their error remains in the version-download page. A stalled UI can still delay display; a Windows test is required.

New machine-code regressions cover old and unknown callbacks at the same retry path, immutable success, active-row retirement distinction, synchronous observer calls and timeout isolation, and failed-group activity/count removal at both image bases. Portable production-cache tests use real isolated host files and SHA1 plus Win32 substitutes to cover transient read/copy/move locks, bounded persistent lock handling, immediate permanent errors, cancellation, and existing integrity cases. Neither test simulates real HTTP traffic or proves the cause of every user-reported failure. Native/network errors still need the user's EXE-side MCPCBox-native-download.log if they persist.

# v17 UI and initial language update

The completed-download pane now uses a separate dismissible, bounded-height output box in normal document flow, so long results do not overlap rows. Passive revision reloads no longer open success notices. Active mutations keep the close button disabled until the result arrives. Record-only removal and resources-only physical deletion remain separate.

The catalog keeps descriptions, parallel options and diagnostics collapsed by default. Buttons switch immediately to preparing, then downloading, with other versions blocked and labelled as waiting. Aggregate progress and reuse statistics remain visible; per-file strings are inside collapsed details. Terminal notices can be dismissed; status JSON now has a per-process taskId so a second run of the same version is distinguishable. Dismissal uses page state and sessionStorage when available. Overlapping polls are prevented and pre-submission responses are discarded by a local generation counter. Submission failures stay visible/dismissible instead of being replaced by an older finished task. XHR callbacks are guarded against duplicate completion. Worker-creation failure now sets a terminal failed status.

first_language.h selects the exact Simplified Chinese case from the verified official asset index (zh_CN.lang / zh_cn.lang / zh_cn.json); pre-index release 1.1 through 1.5 have a narrow legacy fallback. Earlier and unknown unsupported layouts are skipped. On successful full installation, before registration, it writes options.txt only if absent. It uses CREATE_NEW for its temporary file, checks/creates safe parent directories, flushes, then publishes without MOVEFILE_REPLACE_EXISTING. A concurrent target creation is preserved. Existing files are never read or rewritten. Failures are nonfatal install warnings and log entries; client-only probes do not initialize settings. This covers newly installed versions, not a launch hook for all existing or manually imported games. Actual original launcher working-directory behavior remains a Windows validation item.

Reference consulted: PCL ModLaunch.vb, https://github.com/Meloong-Git/PCL/blob/main/Plain%20Craft%20Launcher%202/Modules/Minecraft/ModLaunch.vb (blob SHA 504cd968c153c6924e083436d1210f2400004603), language-code compatibility comments and options.txt usage only. No implementation copied.

New tests execute production first_language.h using real isolated host files plus substituted Win32 APIs, checking old/current official fixtures, lowercase .lang, unsupported versions, preserved settings, write/publication failure cleanup, race and unsafe paths. Frontend DOM/XHR tests exercise terminal close for complete/failed/cancelled, task identity, button labels, stale polling and submission failure. Embedded IE rendering and actual Windows/game startup remain untested. See README.md for reproducible commands and remaining release checks. Prior 360 detection remains unresolved.

# v16 verified shared cache and responsibility correction

File transfers still use original CDownloadManager/taskmodulehttp.dll. The native provider now targets <configured download root>/resources/official/objects/<digest prefix>/<SHA1>.part. cache_keys.h canonicalizes and validates exactly 40 hex digits before path construction. cache_pipeline.h checks a verified existing installation (seed cache if needed), a verified object, or a verified complete .part; only missing/corrupt content invokes the existing native provider. Complete objects are published via same-directory MoveFileEx and independently copied into the unchanged game/<id>/.minecraft tree using cache_copy.h: temporary CopyFile, official SHA1+size verification, atomic replace. No installation hardlinks, custom binary HTTP transfer, archive re-packing, or automatic installed-directory migration are introduced. Cache adds disk space and hashing/copying; first cold downloads may not be faster.

64 process-lifetime critical sections, selected by digest FNV, serialize same-object acquisition across workers. The lock spans native transfer/publication/materialization so duplicate content in one task cannot race its .part and .mcbox.tmp. Other stripes retain original 4/8/16 concurrency. Existing global single-job behavior, pause/cancel, original completion events and retry timing remain. Incomplete parts are handled by the original engine; actual range-resume is not claimed or Windows-tested. A verified part recovers a failed publication without another native provider call. Copy or commit failures preserve complete cache data and do not publish unverified installation files.

Hashed metadata uses resources/official/metadata/<SHA1>.json. Its cached bytes are checked against the currently supplied official digest, optional expected size and JSON parser before reuse. Misses call the existing metadata-only WinHTTP fetcher and save atomically after original validation. The mutable official version list retains the existing catalog refresh/fallback behavior; a full offline launcher is not promised. versions/<id>/files.json records expected file paths/digests/sizes and completion, not duplicate payloads; client probes use client-probe.json. The descriptors are not trusted as input to installation: the installer still builds a plan from verified official metadata. Installation JSON, native extraction and resource mapping use the independent installed copies.

Aggregate center records now point to the version cache-index directory, not the installed game root. Download-center deletion blocks every grouped version-task record, and ordinary file deletion requires the stored path to be strictly under the current configured resources directory, in addition to existing path/type/alias safeguards. The backend no longer calls adapter_unregister from download-history cleanup. Existing original game-management functionality is retained for uninstall. Frontend disables file deletion when groups are selected and directs uninstall to game management. Shared-object per-version garbage collection is not implemented; users can clear the entire cache while the box is closed without deleting independent installed copies. Process-local aggregate history is unchanged, while cache files persist on disk.

Status exposes cacheHits, cacheBytes, localHits, reusedBytes and metadataHits. Cache/local hits credit logical file progress once; the native-transfer branch keeps its existing accounting. Overall native progress remains capped at 99 until full install finishes; the web progress now matches that cap while active. Final logs distinguish verified cache reuse from installed-file reuse. A failure after transfer but during cache publication/copy can leave download byte progress credited while the job is failed; success is not reported until the installation flow finishes.

Validation: tests/test_cache.c includes the PRODUCTION cache_keys.h, cache_copy.h and cache_pipeline.h. It uses real isolated POSIX temporary files and OpenSSL SHA-1, with host substitutes for Windows file calls and the native downloader. It checks cross-install reuse with one provider call, installed seeding, corruption repair, complete-part recovery, incomplete/bad transfer, copy/commit/cancellation and unsafe-path failures, independent installed copies after cache deletion, strict resources-boundary checks, and same-digest locking using pthread mutexes corresponding to the production Win32 lock design. ASan/UBSan passed with ASAN_OPTIONS=detect_leaks=0 because LeakSanitizer cannot inspect the tool environment. Tests do not execute Windows CryptoAPI or actual taskmodulehttp transfer.

Existing tests/test_adapter.py and test_entry.py execute compiled i386 code at preferred/rebased image locations with Windows/original API stubs; tests/test_ui.js checks cache statistics and history UI tests ensure grouped tasks cannot submit file deletion. The former file/shell helper tests remain but grouped directory deletion is unreachable from the v16 download-center endpoint. No real Windows cache transfer/resume, metadata-cache runtime, embedded IE, disk timing, restart configuration or game launch validation. The original exact v4 EXE and matching option/task DLL fixtures are required by machine tests and are not redistributed.

Build: MinGW i686 GCC, Python pefile; native tests need Unicorn; Node frontend tests. Portable cache test needs host OpenSSL development files and pthread (test-only; no OpenSSL dependency is linked into MCPCBox.exe). Shared cache runtime uses Windows CryptoAPI and existing Win32 file APIs. 360 detection remains unresolved; no evasion, packing, anti-analysis or security-product bypass is added.
